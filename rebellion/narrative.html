The Rebellion

interactive terminal investigation // current build // your eyes only

This is not a normal landing page. It is a playable investigation. Participants receive one link and are dropped into a believable Linux terminal. Every discovery is earned by typing commands, inspecting logs, following SSH trails, decrypting a surviving database, and optionally finding a hidden final endpoint.

The tone is cinematic hacker-core, but the interaction language is grounded in real Unix behavior: command history, Tab completion, pipes, chained commands, file paths, SSH confirmation prompts, SQLite, and forensic command output.

// What The Participant Actually Does

The path is split across three machines. Each window below is rendered in its own server's voice — read it like you're already inside that box.

Lines marked * in the left gutter are optional — forensic colour, not the shortest path. The unmarked lines are the spine: the minimum a participant must type to keep moving and reach the reveal. A fast player can ignore every *; a thorough one is rewarded for chasing them.

// Current Technical State

  • All participant pages talk to the same backend endpoint. Story content (files, command outputs, SSH routes, fake filesystem, SQLite responses, final reveal) is served from the backend, not the HTML.
  • Easy edit block: STORY_CONFIG at the top of the backend handler controls character and organisation names and reveal copy.
  • Bash behaviour: path state, Tab completion, globs, pipes, chained commands, history, find, wc, grep, head, tail, which, plus reflex commands a real analyst reaches for (sudo -l, sha256sum with real hashes, dmesg, journalctl, free, w) and realistic denials for filesystem-destroying commands — all server-driven.
  • The box reacts. The backend tracks per-session state and returns delayed reactions the client fires as alert lines: killing the beacon respawns it under a new PID (and every ss/ps/lsof stays consistent with the live PID afterward); reading breach.log or decrypting 017 draws a response from the other people on the wire.
  • Decrypt accepts the real thing: the authentic openssl enc -d -aes-256-cbc … -kfile … works; decrypt <key> <file> is a shorthand alias.

// Notes

  • Give participants only server1.html at the start.
  • Do not mention Server 3 unless they finish the main path or explicitly hunt for secrets. The reveal date is already reachable in Stage 2 (entries); Server 3 is the optional bonus act.
  • Shortest path vs. completionist: the spine (unmarked lines) is roughly cat notes.txt → ssh → cat breach.log → decrypt → sqlite3 → SELECT * FROM entries;. Everything marked * is corroboration a thorough player will chase but a fast one can skip.
  • Hint in-world: "check the logs", "what did SSH remember?", "look at file sizes", "try Tab".
  • For story revisions, edit the backend handler first. HTML should mostly be visual and interaction polish.
  • For real access control, do not rely on GitHub Pages obscurity. Use S3/CloudFront signed URLs, Cloudflare Access, or a token gate.
